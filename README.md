# Personal Food Parser

Локальный парсер рецептов и планировщик питания. Python, Streamlit, SQLite.

Готовы все этапы ТЗ: сбор и нормализация рецептов, инвентарь, карточки, история, генератор рациона на день, неделю и месяц в смешанном режиме и в режиме «только новые», список покупок, резервные копии.

## Запуск

D:\AI\Python312\python.exe -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\streamlit.exe run app.py
```

```

## Как считается план

`core/meal_planner.py` заполняет приёмы пищи по порядку и сразу расходует запасы на копии. Жёсткие условия отсекают рецепт: техника, время, диета, исключения, бюджет, режим «только новые», оценка «не понравилось». Мягкие меняют баллы: покрытие запасами, близкий срок годности, разнообразие, оценки. Веса лежат константами в начале файла.

Приблизительные значения, на которые стоит смотреть с поправкой:

- КБЖУ (`core/nutrition.py`) — оценка по составу и средним значениям на 100 г.
- Цены для бюджета (`PRICE_PER_KG`) — грубые средние по категориям.
- Вес штук и объёмы (`core/units.py`) — средние значения, плотность считается как у воды.
- Время по шагам, помеченное «около», считается как сумма указанных шагов плюс 5 минут на шаг без времени.

## Онлайн-версия и сохранение данных

На Streamlit Cloud диск временный, поэтому записи пользователя сохраняются в приватный репозиторий GitHub (`core/cloud_sync.py`). Рецепты туда не входят. Настройка в Secrets приложения на Streamlit:

```toml
GITHUB_TOKEN = "токен с правом записи только в этот репозиторий"
DATA_REPO = "логин/food-parser-data"
```

Без этих значений приложение работает только с локальной базой.

## Аккаунты

Аккаунты включаются секретом `DATABASE_URL` (`core/accounts.py`, `interface/components/auth.py`). Тогда без входа страницы не открываются, у каждого пользователя свои запасы, планы и история, а резервные копии и загрузка файла базы в настройках скрыты.

1. Создайте проект на supabase.com. В Project Settings → Database → Connection string выберите **Session pooler** и скопируйте адрес вида `postgresql://postgres.xxxx:ПАРОЛЬ@aws-0-....pooler.supabase.com:5432/postgres`. Спецсимволы в пароле кодируются: `@` → `%40`.
2. Добавьте в Secrets приложения на Streamlit:

```toml
DATABASE_URL = "postgresql://..."
OWNER_EMAIL = "почта владельца"  # при первом входе с ней подтянутся данные, сохранённые раньше на GitHub
```

3. Подтверждение почты кодом включается настройками SMTP в тех же Secrets. Без них вход работает без кода, а данные с GitHub не переносятся, потому что почта не подтверждена.

```toml
SMTP_HOST = "smtp.yandex.ru"  # или smtp.gmail.com
SMTP_PORT = "465"
SMTP_USER = "адрес ящика, с которого уходят письма"
SMTP_PASSWORD = "пароль приложения из настроек почты, не основной пароль"
SMTP_FROM = "тот же адрес"
```

После регистрации и при входе без подтверждения на почту приходит код из 6 цифр. Он действует 15 минут, даёт 5 попыток, новый можно запросить через минуту. Хранится только хеш кода.

Таблицы создаются сами при запуске. На всех включается защита строк (RLS) без правил: публичный API Supabase их не видит, приложение подключается владельцем таблиц.

Защита:
- пароль хранится только хешем scrypt с солью, сравнение за постоянное время;
- после 5 неверных паролей вход блокируется на 15 минут;
- ошибка входа одна для неверного пароля и несуществующей почты;
- события входа пишутся в `audit_log`, пароли и данные в журнал не попадают, почта маскируется;
- база пользователя на сервере называется по его id, файлы других пользователей недоступны.

Сессия живёт, пока открыта вкладка: после перезагрузки страницы нужно войти снова.

Для проверки на компьютере: `DATABASE_URL = "sqlite:///data/accounts.db"` в `.streamlit/secrets.toml`.

## Журнал

Журнал пишется в консоль (на Streamlit Cloud: Manage app → Logs) и в `data/logs/app.log`, файлы по 1 МБ, хранятся последние 5. Туда попадают запуск, входы, ошибки сохранения и ошибки страниц с трассировкой.

## Платежи и чеки

Таблицы `payments` и `receipts` готовы, настоящей оплаты нет. Тарифы и цены задаются в `PLANS` (`core/accounts.py`). `create_payment` создаёт платёж, `mark_paid` после подтверждения от платёжного сервиса продлевает тариф и создаёт чек прихода. Чтобы принимать деньги, нужны ИП или самозанятость, договор с платёжным сервисом (например, ЮKassa) и отправка чеков в налоговую через него.

## База данных

- Файл: `data/food_parser.db`. Создаётся при первом запуске.
- Схема меняется только новой записью в конце `MIGRATIONS` в `database/migrations.py`.
- Копии лежат в `data/backups`. Они создаются раз в сутки при запуске и перед каждой миграцией, хранятся последние 20.
- Восстановление: `restore_backup(path)` из `database/database.py`. Текущее состояние перед этим сохраняется отдельной копией.

## Сбор рецептов

```powershell
.venv\Scripts\python.exe -m parser
```

Параметры: `--source имя` (один источник), `--limit N` (страниц за запуск). Сбор можно прервать и запустить снова: готовые страницы пропускаются. Страницы с ошибкой пробуются заново при каждом запуске.

Рецепты сначала попадают в таблицы `raw_items` и `raw_recipes` в исходном виде, затем нормализуются в `recipes`, `ingredients`, `recipe_ingredients`, `cooking_instructions` и `recipe_equipment`. Запись находится по `source_url`, поэтому повторный запуск не меняет id рецептов и не трогает историю.

Только нормализация, без сбора (удобно после правки правил):

```powershell
.venv\Scripts\python.exe -m parser --normalize-only
```

Разбор строк лежит в `parser/normalizer.py`, сопоставление продуктов — в `core/ingredient_matcher.py`. Новый продукт или синоним добавляется в `KNOWN_INGREDIENTS`, а связка, подтверждённая пользователем, запоминается через `add_alias`.

Источник: [Кулинарная книга Викиучебника](https://ru.wikibooks.org/wiki/Кулинарная_книга), лицензия CC BY-SA 4.0. Используется официальный дамп (`data/sources`, около 21 МБ): файл перекачивается, только если на сервере вышла новая версия, а без сети сбор работает на уже скачанном.

Новый источник: класс-наследник `BaseSource` в `parser/sources` и строка в `SOURCES` в `parser/sources/__init__.py`. Для сети есть `PoliteClient`: он соблюдает robots.txt и паузы, повторяет запрос при 429 и сбоях, докачивает файлы.
